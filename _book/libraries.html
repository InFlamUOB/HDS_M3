The libraries

Almost nothing in this booklet is written from scratch. Each exercise is mostly a sequence of calls into libraries other people maintain, and a large part of learning either language is learning which library owns which job. This page is the map: what each one is for, where in the booklet you meet it, and where to read more when the exercise moves faster than you would like.

A note on vocabulary. R calls them packages and loads them with library(dplyr); Python calls them modules or packages and loads them with import pandas as pd or from sklearn.metrics import roc_auc_score. The difference matters in one practical way: library(dplyr) puts every dplyr function within reach, whereas Python makes you name what you want. That is why R code reads filter(...) and Python code reads pd.read_csv(...) — the prefix tells you where the function came from, and in R you have to remember.

R

The tidyverse — getting data into shape

tidyverse is not one package but a family that shares a design: data frames in, data frames out, verbs that read as English, and the pipe (|> or %>%) to chain them. library(tidyverse) loads them all at once; the exercises usually load only the two or three they need, so you can see which does what.

Package What it does Where you meet it
readr reads .csv into a data frame — read_csv() every exercise
dplyr the verbs: filter, select, mutate, group_by, summarise, arrange every exercise
ggplot2 plots built by adding layers — ggplot() + geom_point() wherever there is a figure
tidyr reshaping between wide and long — pivot_longer() 2.1, 2.3, 5.2
patchwork puts two ggplots side by side with + 2.3

The one idea worth carrying away: a dplyr pipeline is a sentence. data |> filter(age > 60) |> summarise(mean(los)) reads left to right in the order the work happens, which is why R code in this booklet rarely needs intermediate variables.

tidymodels — fitting and evaluating

tidymodels is to modelling what the tidyverse is to data handling: a family of packages with one grammar. Its central idea is that specifying a model is separate from fitting it, and separate again from which implementation does the arithmetic. You will see this in Exercise 4.1, where the same specification is sent to two different engines.

Package What it does Where you meet it
parsnip one vocabulary for many models — linear_reg(), logistic_reg(), rand_forest() Day 4 onwards
recipes preprocessing as a fitted object — step_normalize(), step_impute_mean() 2.4, 2.5
rsample splitting and resampling — initial_split(), vfold_cv() 2.5, Day 5
yardstick metrics — rmse(), roc_auc(), sens(), spec() Day 5

Engines. set_engine("ranger") means “fit this random forest using the ranger package”. The specification stays the same; the engine is swapped. Three engines appear in the booklet and each is a package in its own right:

Engine Package Used for
"lm", "glm" base R linear and logistic regression
"rpart" rpart a single decision tree
"ranger" ranger random forests, fast
"glmnet" glmnet lasso and ridge

scikit-learn

scikit-learn is the whole of Days 3 to 9 on the Python side, and it earns a paragraph of its own because its design is the thing to learn, not its function names. Every object follows the same contract: .fit(X, y) learns from data, .transform(X) or .predict(X) applies what was learned, and .fit_transform() does both. Once you know that, a model you have never seen before is usable in one line.

It is organised into submodules, and the booklet uses nine of them:

Submodule What lives there
linear_model LinearRegression, LogisticRegression, Lasso
model_selection train_test_split, cross_val_score, GridSearchCV
metrics mean_absolute_error, roc_auc_score, confusion_matrix
preprocessing StandardScaler, MinMaxScaler, OneHotEncoder
pipeline Pipeline — the object that makes leakage hard to commit
compose ColumnTransformer — different preprocessing per column
impute SimpleImputer, IterativeImputer
tree, ensemble DecisionTreeClassifier, RandomForestClassifier
inspection permutation_importance, partial_dependence
dummy DummyClassifier — the baseline you must beat

The scikit-learn user guide is unusually good: it explains the statistics as well as the code, and is worth reading for its own sake.

The same job in both languages

Job R Python
read a csv readr::read_csv() pandas.read_csv()
filter rows dplyr::filter() df[df.col > x] or df.query()
group and summarise dplyr::group_by() \|> summarise() df.groupby().agg()
plot ggplot2 matplotlib
split train/test rsample::initial_split() train_test_split()
preprocess without leaking recipes inside a workflow() Pipeline + ColumnTransformer
fit a model parsnip spec \|> fit() estimator.fit(X, y)
score it yardstick sklearn.metrics

The pairings are close enough that the hard part is never the translation. It is remembering that set.seed(42) and random_state=42 do not produce the same split, which Exercise 1.2 makes you prove to yourself.

If a library is missing

A missing package produces Error in library(x) : there is no package called 'x' in R, or ModuleNotFoundError: No module named 'x' in Python. Install it:

install.packages("naniar")
pip install shap

Then start a fresh R or Python session — a library installed mid-session is not always visible to the session that was already running.
