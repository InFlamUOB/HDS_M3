13  Exercise 4.1 — One interface, many models

13.1 Objectives

  • Say what a model specification is, what an engine is, and which of the two you change to swap one algorithm for another.
  • Fit three different models to the same rows by changing one line each time, and score each against a baseline that does no learning.
  • Say what a workflow or a Pipeline carries that a fitted model on its own does not.

13.2 Why this, here

In Chapter 2 you wrote the five steps out by hand, with lm() in R and LinearRegression() in Python. That is affordable for one model. From today the models multiply — logistic regression now, trees and forests on Day 5 — and each one of them has its own function name, its own argument names and its own way of returning a prediction. rpart() wants method = "class"; randomForest() wants the outcome to be a factor and will quietly do regression if it is not; glmnet() refuses a formula and demands a matrix.

Two ecosystems exist to put one interface in front of all of that: tidymodels in R and scikit-learn in Python. The point of this exercise is not that they save typing. It is that they make models comparable: when the only line that differs between two analyses is the one naming the model, the difference in the result is attributable to the model.

The question tidymodels scikit-learn
what kind of model is this logistic_reg(), decision_tree() the estimator class, LogisticRegression
which code actually fits it set_engine("glm") the class, plus solver=
what happens to the data first a recipe() of step_*() transformers, e.g. StandardScaler
the two bolted together workflow() Pipeline
fit it, then use it fit(), predict() .fit(), .predict()

13.3 A specification is not a model

Declaring a model and fitting it are separate acts, and both frameworks make you notice. In R you can print a specification that has never seen data. In Python the estimator exists, but asking it to predict raises an error until you fit it.

  • R
  • Python
library(tidymodels)

log_spec  <- logistic_reg(mode = "classification") |> set_engine("glm")
tree_spec <- decision_tree(mode = "classification") |> set_engine("rpart")

log_spec
#> Logistic Regression Model Specification (classification)
#> 
#> Computational engine: glm
from sklearn.linear_model import LogisticRegression
from sklearn.exceptions import NotFittedError

log_spec = LogisticRegression(C=float("inf"), max_iter=1000)

try:
    log_spec.predict([[120.0, 30.0, 40.0]])
except NotFittedError as e:
    print(str(e).split(".")[0])
#> This LogisticRegression instance is not fitted yet

The R specification says logistic regression, fitted by glm and nothing else: no data, no coefficients. Swapping "glm" for "glmnet" keeps the first half and replaces the second.

13.4 The split we use all day

data/diabetes.csv holds 768 adults screened for type 2 diabetes: eight measurements from a single visit and diabetes, which is pos or neg.

We hold back every fifth row. That is not how you would usually split, and the reason we do it here is worth a paragraph.

NoteWhy a fixed rule rather than a seed

Chapter 2 showed that set.seed(42) and random_state=42 select different rows, so the two languages ended the day with different test sets and different scores. That is honest, but it means any R-versus-Python difference you then see is confounded with the split.

Taking every fifth row of a file whose row order carries no information gives both languages the same 153 patients, so the rest of this day compares languages rather than partitions. Exercise 1.2’s Stretch 2 asked how much the split matters; Stretch 1 below is that question again, and the answer is still “more than you would like”.

  • R
  • Python
library(readr); library(dplyr)

diabetes <- read_csv("data/diabetes.csv", show_col_types = FALSE) |>
  mutate(diabetes = factor(diabetes, levels = c("neg", "pos")))

test_rows <- seq(5, nrow(diabetes), by = 5)
train <- diabetes[-test_rows, ]
test  <- diabetes[ test_rows, ]

c(train = nrow(train), test = nrow(test), test_pos = sum(test$diabetes == "pos"))
#>    train     test test_pos 
#>      615      153       55
import pandas as pd

diabetes = pd.read_csv("data/diabetes.csv")

is_test = (diabetes.index + 1) % 5 == 0
train, test = diabetes[~is_test], diabetes[is_test]

y_train = (train["diabetes"] == "pos").astype(int)
y_test  = (test["diabetes"] == "pos").astype(int)
features = ["glucose", "mass", "age"]

len(train), len(test), int(y_test.sum())
#> (615, 153, 55)

13.5 Fit and predict: the same two verbs, whatever the model

  • R
  • Python
log_fit  <- log_spec  |> fit(diabetes ~ glucose + mass + age, data = train)
tree_fit <- tree_spec |> fit(diabetes ~ glucose + mass + age, data = train)

acc <- function(f) mean(predict(f, test)$.pred_class == test$diabetes)
c(logistic = acc(log_fit), tree = acc(tree_fit),
  majority = mean(test$diabetes == "neg"))
#>  logistic      tree  majority 
#> 0.7124183 0.6928105 0.6405229
from sklearn.tree import DecisionTreeClassifier

log_fit  = LogisticRegression(C=float("inf"), max_iter=1000).fit(train[features], y_train)
tree_fit = DecisionTreeClassifier(random_state=42).fit(train[features], y_train)

{"logistic": round(log_fit.score(test[features], y_test), 4),
 "tree":     round(tree_fit.score(test[features], y_test), 4),
 "majority": round(float((y_test == 0).mean()), 4)}
#> {'logistic': 0.7124, 'tree': 0.5948, 'majority': 0.6405}

Two readings, and the second is the uncomfortable one.

The logistic regressions agree: 0.712 in both languages, on the same 153 patients. The trees do not — about 0.69 in R against about 0.59 in Python — and the word decision_tree is identical in both. rpart stops growing when a split stops paying for itself, so it returns ten leaves; DecisionTreeClassifier grows until every leaf is pure, so it returns about 180 and scores 1.00 on the rows it was fitted to. Same name, same data, different default, and the default is the whole difference. Chapter 19 is where you learn to control it.

And a third reading, which should take the shine off all of them: always saying neg scores 0.641 on this test set. The logistic model’s seven percentage points over that is the entire return on three clinical measurements.

TipStuck?

The R side wants the same formula and the same data frame you gave fit() for the logistic model. The Python side wants the predictor columns and the outcome as two separate arguments — that is the shape difference from Exercise 1.1, and it has not gone away.

A forest has no coefficients, no equation and no way of telling a clinician why it said what it said. It also, here, does not win: five hundred trees score about 0.69–0.70 against the logistic regression’s 0.712 on the same rows. Note that down before Chapter 20, and note too that the cost of finding it out was one line — which is the argument for the framework, and the only argument this exercise is making.

13.7 Task 2 — Swap the engine, keep the model

Now change only the second half of the specification. In R, replace the glm engine with glmnet, which fits the same logistic model with a penalty on the coefficients. In Python there is no engine slot; the nearest thing is solver=, so change that instead and see whether it does the same job.

  • R
  • Python
# Replace every ______ below, then run this cell.
lasso_fit <- logistic_reg(penalty = 0.1, mixture = 1) |>
  set_engine("______") |>
  fit(diabetes ~ glucose + mass + age, data = train)

round(coef(lasso_fit$fit, s = 0.1)[, 1], 5)   # compare with the glm coefficients
round(coef(log_fit$fit), 5)
# Replace every ______ below, then run this cell.
import numpy as np
for solver in ["lbfgs", "newton-cg", "______"]:
    m = LogisticRegression(C=1.0, solver=solver, max_iter=1000).fit(train[features], y_train)
    print(f"{solver:>10}", np.round(m.coef_[0], 5), round(m.intercept_[0], 3))

In R the engine change is a change of model: the lasso drives the coefficients for mass and age to exactly zero and keeps only glucose. Two of your three predictors have left the building, and nothing in the specification said they could.

In Python two of the three solvers agree to four decimal places and the third, liblinear, does not — it penalises the intercept as well, which the other two do not. So “the solver is only a numerical detail” is true twice out of three times, which is the worst possible number of times for a thing to be true.

NoteAssign the result of .fit(), always

Written as a bare line, pipe.fit(X, y) returns the fitted pipeline, and both Jupyter and this booklet will then print scikit-learn’s HTML representation of it — the grey box listing every default parameter. It is noise in a notebook, and in a knitr render under a non-UTF-8 locale it stops the build outright. Assign the result, or end the line with a semicolon.

Compare the standardised coefficients with the unstandardised ones from the earlier cell. The accuracy is unchanged at 0.712 — an unpenalised logistic regression does not care about the units of its predictors — but the coefficients now say something the originals could not: per standard deviation, glucose carries about four times the weight of mass or age.

NoteTwo things differ between the languages here, and only one matters

R reports the standardised glucose coefficient as about 1.1804 and Python as about 1.1794. The cause is that step_normalize() divides by the sample standard deviation (dividing by \(n-1\)) and StandardScaler by the population one (dividing by \(n\)). It is a convention, it is a fourth decimal place, and it never changed a clinical conclusion.

The difference that does matter is in the next section.

The reason to put the scaling inside the object rather than before the split is leakage: a scaler fitted on all 768 rows has read the test set’s mean. That is Chapter 7’s subject and this is the machinery that prevents it.

13.9 The result that should bother you

The two frameworks give you the same interface. They do not give you the same model.

  1. On these 615 training rows, R’s glm and scikit-learn with C=inf agree to five decimal places: glucose 0.03508, mass 0.03598, age 0.02170. Whatever else is going on, the two libraries solve the same problem when you ask them to.
  2. But C=inf is not scikit-learn’s default. The default is C=1.0, which is an L2 penalty on the coefficients — the thing the glmnet engine does in R only when you ask for it. On 615 rows the penalty is swamped by the likelihood and you cannot see it.
  3. Run the cell below, which refits on the first 50 rows only. Now you can.
  • R
  • Python
small <- diabetes[1:50, ]
z <- function(x) (x - mean(x)) / sd(x)
glm_small <- glm(diabetes ~ z(glucose) + z(mass) + z(age) + z(pedigree),
                 data = small, family = binomial)
round(coef(glm_small), 3)
#> (Intercept)  z(glucose)     z(mass)      z(age) z(pedigree) 
#>      -1.118       0.799      -0.022       0.101       0.968
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler
import numpy as np

small = diabetes.iloc[:50]
y_small = (small["diabetes"] == "pos").astype(int)
f4 = ["glucose", "mass", "age", "pedigree"]

for C, label in [(float("inf"), "no penalty"), (1.0, "the default")]:
    p = Pipeline([("scale", StandardScaler()),
                  ("model", LogisticRegression(C=C, max_iter=2000))]).fit(small[f4], y_small)
    print(f"{label:>12}", dict(zip(f4, np.round(p[-1].coef_[0], 3))))
#>   no penalty {'glucose': np.float64(0.791), 'mass': np.float64(-0.022), 'age': np.float64(0.1), 'pedigree': np.float64(0.959)}
#>  the default {'glucose': np.float64(0.663), 'mass': np.float64(0.035), 'age': np.float64(0.117), 'pedigree': np.float64(0.751)}

Unpenalised, mass has a coefficient of −0.022; at the default C=1.0 it is +0.035. Fifty patients, four predictors, and the sign of a clinical association depends on an argument nobody typed. R’s unpenalised glm gives −0.022 too: it matches the unpenalised Python fit, not Python’s default.

The lesson is not that scikit-learn is wrong — a penalty on 50 rows is good statistics, and Day 5 will argue for it. The lesson is that “I fitted a logistic regression” does not identify a model, and a methods section that says only that cannot be reproduced in the other language.

13.11 Stretch

NoteStretch 1 — How much of today is the split?

Replace the every-fifth-row rule with initial_split(diabetes, prop = 0.8, strata = diabetes) under ten different seeds, and collect the ten logistic accuracies. Ours ran from about 0.69 to 0.80. The majority baseline moves too. Report the range, and then decide what you think of a paper that reports one split and three decimal places.

NoteStretch 2 — Make the tree behave

Grow the scikit-learn tree with ccp_alpha=0.01 and refit. The test accuracy rises from about 0.59 to about 0.71. You have not changed the algorithm, the data or the split — only the default that decides when to stop. Keep the number: Chapter 19 is about why pruning is the whole game.

13.12 What you can and cannot now claim

Can: that you can fit, swap and score models through one interface in either language, and that you know which line to change to swap the algorithm, the engine or the preprocessing.

Cannot: that any of these models is any good. Every number on this page is an accuracy, and accuracy on a 36% prevalence outcome is a weak instrument — 0.641 of it is free. Before judging a classifier you need to know what it predicts for an individual patient, which is a probability, and that is Chapter 14.
