How to use this booklet

This is the exercise booklet for Module 3 of the Health Data Science MSc. It is organised by teaching day: each day is a part of the book, and each chapter inside a day is one exercise you can finish in a single sitting.

Each exercise is code to read and copy. The worked examples are shown with the output they produce, so you can compare your own result against ours. You run the code in R or Python on your own machine — Appendix A — Running it on your own machine is the install guide, and it is worth doing before the first session.

Tasks appear as code containing ______ for you to fill in. They are shown but not run, which is why no output appears beneath them.

Why both languages

Most health data science teams use one language for data management and the other for modelling, and the ability to read a colleague’s code in the language you do not prefer is worth more than fluency in either. Every exercise therefore has an R path and a Python path doing the same work, in tabs. The booklet is explicit about the places where the two genuinely differ rather than pretending one is a translation of the other.

What each chapter looks like

  1. Objectives — what you will be able to do, phrased so you can test whether you can do it.
  2. Worked example — code shown with its output. Nothing is hidden; the point is to see a correct pipeline before you build one.
  3. Tasks — code with ______ for you to fill in, in your own script. Most have a Stuck? hint, and a Check yourself call that inspects the object you just made.
  4. Stretch — optional, for when you finish early. Not harder versions of the task; the question the task raises.
  5. What you can and cannot now claim — the sentences you could defend to a clinician on the basis of what you just did, and the ones you could not.

The self-checks

Tasks call helpers such as check_split() or check_beats_baseline(). They are not graded and nothing is submitted. They exist because the most expensive mistake in a first ML pipeline is not a wrong answer but a silently wrong object — a split that leaks, a column read as text, a model fitted to the test set — which produces a number that looks entirely reasonable. Each check prints what it inspected, so a failure points you at where to look.

A check that passes does not mean your answer is right. It means your answer is not wrong in the specific way the check knows about.

Worked answers

The answer to each task, with its output, is published after the session it belongs to. Until then it is not on the page at all, so there is nothing to peek at — which is the point: the exercise is worth more than the answer.

Where the data comes from

Every dataset here is simulated, by a script you can read: scripts/make_data.R. Because we wrote the data-generating process, we know the true answer to every question asked, so you can find out whether your diagnosis was right rather than merely plausible — a luxury you will never have again once you work with real patient data. Appendix B — The datasets gives the generating equations and the known defects of each file.
