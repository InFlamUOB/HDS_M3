20  Exercise 5.4 — Random forest, and what the pipeline bought you

Every cell on this page is a real R or Python cell, run against data/diabetes.csv with the split used throughout Day 5.

20.1 Objectives

  • Fit and tune a random forest through a workflow, changing only the model specification from the one you wrote in Chapter 19.
  • Say why the training performance of a bagged model is not evidence of anything, and name the number to report in its place.
  • Decide, with a standard error in hand, whether a more flexible model has actually beaten a simpler one.

20.2 Why this, here

Chapter 19 ended with a tuned tree that was behind a logistic regression, and with the observation that a single tree is unstable: resample the training rows and the splits three levels down change. Instability of that kind is variance, and variance can be averaged away. A random forest grows hundreds of trees, each on a bootstrap resample of the rows and each allowed to consider only a random handful of predictors at every split, and averages their votes. The decorrelation is the point; without it the trees would all look alike and averaging would gain nothing.

You will change four lines of the Day 5.3 code. That is the second thing this exercise is about.

20.3 Worked example — five hundred trees, fitted the same way as one

  • R
  • Python
library(tidymodels); library(readr)

diabetes <- read_csv("data/diabetes.csv") |>
  dplyr::mutate(diabetes = factor(diabetes, levels = c("pos", "neg")))

set.seed(123)
split <- initial_split(diabetes, prop = 0.7, strata = diabetes)
train <- training(split); test <- testing(split)

rf_fit <- rand_forest(trees = 500) |>
  set_engine("ranger", seed = 123) |>
  set_mode("classification") |>
  fit(diabetes ~ ., data = train)

scores <- function(fit, label) {
  one <- function(dat, set) {
    p <- augment(fit, dat)
    tibble::tibble(model = label, set = set,
      accuracy = accuracy(p, diabetes, .pred_class)$.estimate,
      sens     = sens(p, diabetes, .pred_class)$.estimate,
      spec     = yardstick::specificity(p, diabetes, .pred_class)$.estimate,
      auc      = roc_auc(p, diabetes, .pred_pos)$.estimate)
  }
  dplyr::bind_rows(one(train, "train"), one(test, "test"))
}

scores(rf_fit, "rf defaults")

#>   model       set   accuracy  sens  spec   auc
#>   <chr>       <chr>    <dbl> <dbl> <dbl> <dbl>
#> 1 rf defaults train    0.953 0.898 0.985 0.993
#> 2 rf defaults test     0.736 0.536 0.850 0.824
import pandas as pd, numpy as np
from sklearn.model_selection import train_test_split, GridSearchCV, StratifiedKFold
from sklearn.ensemble import RandomForestClassifier
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.metrics import accuracy_score, recall_score, roc_auc_score

diabetes = pd.read_csv("data/diabetes.csv")
X = diabetes.drop(columns="diabetes")
y = (diabetes["diabetes"] == "pos").astype(int)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.3,
                                          random_state=123, stratify=y)

rf_fit = RandomForestClassifier(n_estimators=500, random_state=123,
                                oob_score=True).fit(X_tr, y_tr)

def scores(fit, label):
    rows = []
    for name, Xs, ys in [("train", X_tr, y_tr), ("test", X_te, y_te)]:
        pred = fit.predict(Xs)
        rows.append({"model": label, "set": name,
                     "accuracy": accuracy_score(ys, pred),
                     "sens": recall_score(ys, pred),
                     "spec": recall_score(1 - ys, 1 - pred),
                     "auc": roc_auc_score(ys, fit.predict_proba(Xs)[:, 1])})
    return pd.DataFrame(rows)

scores(rf_fit, "rf defaults")
#>          model    set  accuracy      sens      spec      auc
#> 0  rf defaults  train  1.000000  1.000000  1.000000  1.00000
#> 1  rf defaults   test  0.705628  0.630952  0.748299  0.76806
ImportantDo not read the training row

A random forest’s training accuracy is between 0.95 and 1.00 and it means almost nothing. Each tree was grown on a bootstrap resample, so when you ask the forest about a training patient, roughly two-thirds of its trees are being asked about a row they were fitted on. The average is contaminated by construction, and it is contaminated in a way that no amount of extra data fixes.

Both libraries supply the honest internal alternative: the out-of-bag estimate, computed for each row from only the trees that did not see it. extract_fit_engine(rf_fit)$prediction.error in R gives the OOB Brier score — about 0.18 here, where lower is better. rf_fit.oob_score_ in Python gives OOB accuracy, about 0.76. Report one of those, or the resampled estimate from the tuning below. Never the training row.

extract_fit_engine(rf_fit)$prediction.error   # OOB Brier score
#> [1] 0.1823601

20.7 The result that should bother you

Five hundred trees, two tuned hyperparameters, a grid search over nine settings and five resamples each. The tuned forest reaches a test AUC of about 0.79–0.83. The logistic regression from Chapter 18, eight coefficients and no tuning at all, reaches about 0.78–0.84 on the same rows.

Three steps.

  1. The difference between the two is around 0.01 of AUC. The standard error of the forest’s own resampled estimate is about 0.02. A difference smaller than the uncertainty of the measurement is not a difference, and no amount of decimal places makes it one.
  2. Which direction it falls in depends on the language — which is to say, on which rows landed in the test set. In R the logistic regression is ahead; in Python the forest is, by about the same margin. If a result flips when you reshuffle the data, the result is the reshuffling.
  3. So the honest finding is that on these eight predictors and these 768 patients, flexibility buys nothing. That is a real and publishable finding, and it is the one most often not reported, because a forest that ties with a logistic regression looks like a failed experiment rather than evidence about the data.

A forest that ties should still usually lose. The logistic regression’s coefficients can be inspected, its behaviour outside the training range is predictable, and a clinician can be told what it does. The explainability exercises are about what you have to do to say the same of a forest.

20.8 Reflection — why pipelines

The original version of this exercise asked these two questions and they are the right two.

  1. What do workflows and pipelines give you over writing the model, the formula and the prediction code separately? Answer it concretely: count the lines you changed between Chapter 19 and this page.
  2. How does a workflow help when you change the model, and how does it help when you add preprocessing — scaling, imputation, dummy variables?

The second half is the one with teeth. A preprocessing step fitted outside the pipeline is fitted on all the rows, including the ones being held out, which is Chapter 7’s failure mode. Inside a workflow or a Pipeline, every resampling fold refits the preprocessing on its own training part. The same code is correct under cross-validation and incorrect without the wrapper, and nothing in the output tells you which you did.

20.9 Stretch

NoteStretch 1 — How many trees are enough?

Refit the tuned forest with 10, 50, 100 and 500 trees and plot test AUC against the count. The curve flattens early. What does that say about the common claim that a forest “cannot overfit by adding trees”, and about where the remaining error is coming from?

NoteStretch 2 — Give it a useless predictor

Add a column of random numbers to the training and test data and refit. The test AUC barely moves, which is the forest’s robustness. Then look at what vip::vip() says about the random column’s importance — and keep the answer for Chapter 22.

NoteStretch 3 — Tune for the clinic, not for AUC

Retune with metrics = metric_set(sens) and a threshold that a screening service could live with. Does the chosen mtry change? What has to be true about the service for that to be the right objective?

20.10 What you can and cannot now claim

Can: that you can tune and evaluate an ensemble through the same workflow you used for a single tree, that you report an out-of-bag or resampled estimate rather than a training one, and that you can say whether a difference between two models is larger than the noise in the comparison.

Cannot: anything about why the forest predicts what it predicts for a given patient. Five hundred trees have no coefficients and no drawing. That is the question the explainability exercises exist to answer, and it is the price you have now agreed to pay.
